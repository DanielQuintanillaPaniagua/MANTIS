## 1. Objetivo del hito

Detectar **V2 (BFLA)** y **V3 (state skip)** en el lab de MK-002,
además de V1 (BOLA) que ya detectaba MK-005.

MK-006 introduce:

- Heurísticas de **autorización a nivel de función** (BFLA).
- Heurísticas de **flujo de estados** (state skip).
- **Secuencias de operaciones** (reset → probar → reset → probar).
- Configuración explícita de operaciones privilegiadas.

**No detecta** race conditions, secuencias de más de 3 operaciones,
ni modelos de estado complejos. Eso queda para hitos posteriores.

## 3. Cómo detecta MANTIS V2 (BFLA) sin saber que V2 existe

**Regla genérica:**

> "Si una operación privilegiada (declarada por el usuario) es ejecutada
> con éxito por una identidad limitada B y también por una identidad
> privilegiada A, y el estado del recurso cambia, hay BFLA."

**Pasos:**

1. Resolver ámbitos de A y B con `/me` (heredado de MK-005).
2. Filtrar operaciones de cambio de estado (`POST`, `PUT`, `PATCH`, `DELETE`)
   cuyo path contenga alguno de los marcadores en
   `MantisConfig.privileged_operations`.
3. Para cada operación privilegiada con path param:
   1. Listar recursos visibles para B (la identidad limitada).
   2. Reset lab.
   3. Ejecutar la operación con A sobre un recurso. Leer estado antes y después.
   4. Si A tuvo éxito y el estado cambió, la operación es "válida para A".
   5. Reset lab.
   6. Ejecutar la operación con B sobre el mismo recurso. Leer estado.
   7. Si B tuvo éxito y el estado cambió → **BFLA**.
4. Reportar con `Confidence.MEDIUM`.

**Requisito crítico:** `privileged_operations` debe estar configurado.
Sin él, no se detecta BFLA (limitación documentada en la sección 11).

**Ejemplo en el lab:**

- `privileged_operations=("approve",)`.
- Factura 2 (Norte, `submitted`): admin `approve` → 200, `approved`. Employee `approve` → 200, `approved`. **BFLA.**

## 4. Cómo detecta MANTIS V3 (state skip) sin saber que V3 existe

**Regla genérica:**

> "Si una operación de cambio de estado mueve un recurso desde su estado
> inicial a un estado que **no es el observado en la transición natural**,
> es un salto de estado."

**Pasos:**

1. Requiere `/lab/reset` en el spec. Sin él, no se detecta.
2. Identificar operaciones de cambio de estado con path param.
3. **Fase 1 — descubrir la transición natural:**
   - Para cada operación (en orden de aparición en el spec):
     - Reset lab.
     - Tomar un recurso en estado `draft` (o el primer estado encontrado).
     - Ejecutar la operación con A.
     - Si el estado cambió, **esta es la transición natural**. Registrar y parar.
4. **Fase 2 — probar saltos:**
   - Para cada operación **que no sea la natural**:
     - Reset lab.
     - Tomar un recurso en estado `draft`.
     - Ejecutar la operación con A.
     - Si el estado cambió → **STATE_SKIP**.
5. Reportar con `Confidence.MEDIUM`.

**Ejemplo en el lab:**

- `submit` es natural (`draft → submitted`).
- `approve` sobre `draft` → `approved` es un salto. **STATE_SKIP.**

## 5. Configuración

### `MantisConfig.state_fields`

Campos que representan el estado del recurso. Por defecto:

```python
state_fields = ("status", "state", "phase")
```

### `MantisConfig.privileged_operations`

Substrings de path que identifican operaciones admin-only.
**Requerido para BFLA.** Por defecto vacío (BFLA no se detecta).

```python
privileged_operations = ()  # usuario debe declarar
```

Ejemplo:

```bash
mantis scan <spec> --sequences --privileged-operations approve
```

## 6. CLI

```text
mantis scan <spec> --identity A:key --identity B:key \
    [--sequences] [--privileged-operations SUBSTRING ...] [--max-requests N] \
    [--json] [--base-url URL] [--log PATH] [--no-log]
```

**Modos:**

| Modo | Flags | Detecta |
|---|---|---|
| BOLA only | (sin flags extra) | V1 |
| Full | `--sequences --privileged-operations approve` | V1 + V2 + V3 |
| Sin privilegiadas | `--sequences` | V1 + V3 (no V2) |

`--max-requests` es importante: BFLA y state skip hacen muchas peticiones
(8-10 por recurso). El default de `MantisConfig` (20) puede ser
insuficiente. Con `--max-requests 200` se evita `RateLimitExceeded`.

**Salida humana (con `--sequences`):**

```text

Identity A: admin
Identity B: employee
Mode: BOLA + BFLA + state skip

[HIGH] BOLA-_invoices_{invoice_id}-3
  Type: BOLA
  Confidence: high
  ...
[HIGH] BFLA-_invoices_{invoice_id}_approve-1
  Type: BFLA
  Confidence: medium
  ...
[HIGH] STATE_SKIP-_invoices_{invoice_id}_approve-1
```

## 11. Limitaciones conocidas

### 11.1 — `privileged_operations` es obligatorio para BFLA

MANTIS no adivina qué operaciones son admin-only. El usuario debe
declararlo. Sin `--privileged-operations`, BFLA no se detecta. Es
honesto: sin información de roles, no se puede inferir autorización
a nivel de función.

**Alternativa futura:** inferir de `security` o `tags` del `ApiSpec`
si están declarados. En MK-007+.

### 11.2 — Requiere `/lab/reset` para BFLA y state skip

Sin un endpoint de reset, el estado inicial de los recursos no es
determinista. MANTIS no puede garantizar que A y B actúan sobre el
mismo estado.

En una API real, no hay `/lab/reset`. MK-006 asume que el objetivo
es un lab controlado. Para APIs reales, se requiere otro mecanismo
de aislamiento.

### 11.3 — BFLA puede solaparse con V3

En el lab, `approve` sobre factura 1 (`draft`) dispara:

- **BFLA** (empleado puede aprobar).
- **STATE_SKIP** (admin aprueba `draft` → `approved`).

Ambos se reportan por separado. No es un falso positivo, pero
requiere revisión humana. En MK-007 (regresión) se refinará.

### 11.4 — `_execute` usa `client.post` para todos los métodos

`MantisClient` solo tiene `get()` y `post()`. `_execute` usa `client.post()`
para POST, PUT, PATCH y DELETE. Para el lab (todo POST), funciona.
Para otros métodos, es incorrecto. Se añadirán métodos en `MantisClient`
en un hito futuro si es necesario.

### 11.5 — `--max-requests` necesario en scans con `--sequences`

BFLA y state skip hacen 8-10 peticiones por recurso. El default de
`MantisConfig.max_requests` (20) puede ser insuficiente. Usar
`--max-requests 200` o similar.

### 11.6 — Confianza `MEDIUM` para BFLA y STATE_SKIP

Son heurísticas. Requieren revisión humana. BOLA es `HIGH` porque el caso
es claro (recurso ajeno + 200).

---
### 11.7 — Transiciones de estado (corregido en MK-006.1)

En MK-006, la transición natural se infería por el orden de las operaciones
en el spec. Si `approve` aparecía antes que `submit`, podía considerarse
natural y `submit` reportarse como salto (falso positivo).

En MK-006.1 se añade `MantisConfig.allowed_transitions`, configurable
con `--allowed-transition FIELD:FROM->TO`. Sin esta configuración, se
mantiene la heurística por orden (documentada como frágil).

### 11.8 — Métodos HTTP (corregido en MK-006.1)

En MK-006, `_execute` usaba `client.post()` para todos los métodos,
ignorando el método declarado en `Operation.method`. En MK-006.1 usa
`client.request(method, ...)` con el método correcto.

**Limitación pendiente:** no se envía body. Para PUT/PATCH/POST que
requieran body, esto fallará o producirá resultados erróneos. Se
documenta como pendiente para un hito futuro.
