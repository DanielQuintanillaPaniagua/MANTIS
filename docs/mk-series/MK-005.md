## 1. Objetivo del hito

Que MANTIS detecte automáticamente **al menos una vulnerabilidad
de autorización** en el lab de MK-002, **sin que el motor sepa de
antemano cuál es cuál**.

El éxito no es "encontrar algo". Es:

1. Recibir un `ApiSpec` de MK-004.
2. Generar hipótesis de autorización.
3. Ejecutar peticiones con MK-003.
4. Comparar resultados con la hipótesis.
5. Registrar hallazgos **reproducibles**.
6. **Cero falsos positivos.** Al menos un verdadero positivo.

## 3. Cómo detecta MANTIS V1 sin saber que V1 existe

**Regla genérica aplicada:**

> "Si una identidad accede a un recurso cuyo campo de propiedad
> (`branch_id`, `tenant_id`, etc.) no coincide con el de su propio
> perfil (`/me`), hay una posible violación de autorización por objeto."

**Pasos:**

1. **Resolver el ámbito de cada identidad** llamando a `/me` (o
   `/users/me`, `/profile`). Extraer los campos de
   `MantisConfig.ownership_fields`.
2. **Encontrar operaciones `GET` con path param** en el `ApiSpec`.
   Ej: `GET /invoices/{invoice_id}`.
3. **Listar recursos con la identidad A** (admin), llamando al path
   padre (`GET /invoices`).
4. **Para cada recurso:**
   - A pide el recurso → 200 (asumido).
   - B pide el mismo recurso → 200 o 403.
   - Si B obtiene **200** y el recurso tiene un `ownership_field`
     que **no coincide** con el ámbito de B → **finding BOLA**.

**MANTIS no sabe que las facturas 3 y 4 son "de Sur".** Solo ve que
el empleado (ámbito S001) accede a recursos con `branch_id: S002`.

## 5. Modelo de hallazgo

### `Finding`

| Campo | Tipo | Descripción |
|---|---|---|
| `id` | `str` | Único, ej. `BOLA-_invoices_{invoice_id}_3` |
| `type` | `FindingType` | `BOLA`, `BFLA`, `STATE_SKIP` |
| `severity` | `Severity` | `high`, `medium`, `low` |
| `confidence` | `Confidence` | `high`, `medium`, `low` |
| `operation_method` | `str` | `GET` |
| `operation_path` | `str` | `/invoices/{invoice_id}` |
| `identity` | `str` | `employee` |
| `summary` | `str` | 1 línea |
| `details` | `str` | Descripción completa |
| `evidence` | `tuple[Evidence, ...]` | Peticiones A y B |
| `reproduction` | `tuple[str, ...]` | Pasos mínimos |

### `Evidence`

Metadatos de una petición: `description`, `method`, `url`, `status`,
`response_size`, `error`. **No guarda body completo.** Evita fugas y
tamaño excesivo.

## 11. Notas conocidas

### 11.1 — Solo se detecta V1

MK-005 no detecta V2 (BFLA) ni V3 (state skip). Requieren:

- **V2:** conocer qué operaciones son admin-only. El `ApiSpec` no lo
  declara (el lab no usa `Security(...)` en FastAPI). Requiere
  heurísticas o configuración explícita.
- **V3:** conocer el flujo de estados (draft → submitted → approved).
  El `ApiSpec` no declara transiciones válidas.

Pendiente para MK-006.

### 11.2 — Heurística de `/me`

`_resolve_scope` prueba `/me`, `/users/me`, `/profile` en orden. Si
ninguno devuelve 200 con un `ownership_field`, no se puede detectar
BOLA. Se documenta como limitación.

**Alternativa futura:** configuración explícita del endpoint de
identidad por identidad.

### 11.3 — Fallback de IDs

Si `GET /invoices` (listado) falla, se prueban IDs 1-10. Es un
fallback razonable para labs pequeños. En APIs reales, el listado
suele funcionar.

### 11.4 — API keys en evidencia

El `reproduction` de los findings incluye las API keys truncadas
(`lab-empl...`). La evidencia (`Evidence.url`) incluye la URL completa
sin la API key (va en header). Pero el log de MK-003 sí guarda
headers redactados (MK-003.1).

No hay fuga de secretos en findings. Las keys en `reproduction`
están truncadas a 8 caracteres.

### 11.5 — Confianza alta por defecto

Todos los findings tienen `Confidence.HIGH` porque el caso es claro:
admin ve 200, empleado ve 200, ámbitos difieren. En MK-006+ se
refinará con más heurísticas.
