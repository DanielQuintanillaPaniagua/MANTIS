# MK-009 — Detection Expansion & External Validation

| Campo | Valor |
|---|---|
| Hito | MK-009 |
| Nombre | Detection Expansion & External Validation |
| Estado | En diseño |
| Depende de | MK-008 y sus fases correctivas |
| Precede a | MK-010 — Hardening & Release |

---

## 1. Objetivo

Expandir las capacidades de detección de MANTIS para evaluar APIs con diferentes mecanismos de autenticación, múltiples identidades y operaciones sobre recursos.

MANTIS debe ser capaz de:

1. Detectar BOLA en operaciones GET, PUT, PATCH y DELETE, bajo condiciones seguras y verificables.
2. Soportar una matriz de autorización con múltiples identidades, recursos y operaciones.
3. Calcular severidad y confianza de forma independiente y basada en evidencia.
4. Diferenciar hallazgos confirmados, resultados inconclusos y pruebas omitidas.
5. Ser evaluado contra laboratorios de APIs vulnerables de terceros, como OWASP crAPI y VAmPI.

## 2. Matriz de autorización multi-identidad

Actualmente, MANTIS utiliza dos identidades para realizar comparaciones de autorización.

En MK-009 se ampliará el modelo para admitir N identidades, sujeto a límites configurables.

Ejemplo conceptual:

```bash
mantis scan <spec> \
  --identity admin \
  --identity employee1 \
  --identity employee2
```

Las credenciales se proporcionarán mediante mecanismos seguros de configuración, evitando exponer secretos en argumentos, registros o evidencias.

### Lógica

- Cada identidad tendrá un identificador único y su configuración de autenticación.
- El endpoint de identidad será configurable.
- MANTIS podrá obtener el contexto de cada identidad.
- Se construirá una matriz identidad × recurso × operación.
- Se evaluará el acceso según las reglas de autorización disponibles.
- Los resultados conservarán la evidencia asociada a cada combinación.

La comparación de respuestas por sí sola no constituye prueba suficiente de BOLA. Se requerirá evidencia contextual que demuestre acceso no autorizado.

### Límites

- Número máximo de identidades configurable.
- Límite de peticiones por análisis.
- Timeout por operación.
- Control de concurrencia.

## 3. BOLA en operaciones de escritura

Se ampliará la detección para contemplar:

- GET
- PUT
- PATCH
- DELETE

### Requisitos de seguridad

Las operaciones de escritura solamente se ejecutarán cuando exista una estrategia de restauración segura y verificable.

Para PUT y PATCH:

1. Capturar el estado inicial.
2. Preparar una modificación controlada.
3. Ejecutar la operación dentro del alcance autorizado.
4. Verificar el resultado.
5. Restaurar y verificar el estado original.

Para DELETE:

- Exigir un entorno aislado o una estrategia de restauración verificada.
- Comprobar que el mecanismo de recuperación funciona.
- No ejecutar si no existen garantías suficientes.

Cuando una prueba no pueda ejecutarse:

`OMITTED — motivo explícito`

La imposibilidad de realizar una prueba nunca se interpretará como ausencia de vulnerabilidad.

## 4. Severidad y confianza

Los Findings incorporarán dos propiedades independientes.

### Confidence

Representa la confianza en que el hallazgo es real.

| Nivel | Significado |
|---|---|
| HIGH | Evidencia directa y reproducible |
| MEDIUM | Evidencia consistente pero incompleta |
| LOW | Indicios que requieren verificación |

### Severity

Representa el impacto potencial o demostrado de la vulnerabilidad.

| Nivel | Significado |
|---|---|
| CRITICAL | Impacto extremo |
| HIGH | Impacto grave |
| MEDIUM | Impacto moderado |
| LOW | Impacto limitado |
| INFO | Observación informativa |

La clasificación considerará contexto, impacto, sensibilidad de los datos y alcance de la operación.

No se asignará severidad únicamente por el método HTTP.

## 5. Estados de evaluación

MANTIS diferenciará explícitamente:

- CONFIRMED: vulnerabilidad respaldada por evidencia suficiente.
- NOT_FOUND: la prueba se ejecutó, pero no encontró la condición evaluada.
- OMITTED: prueba no ejecutada, con motivo documentado.
- INCONCLUSIVE: evidencia insuficiente para confirmar o descartar.

Los resultados conservarán las peticiones, respuestas y contexto necesarios para su reproducción, con secretos redactados.

## 6. Validación externa

Se evaluará MANTIS contra:

- OWASP crAPI.
- VAmPI.

Ambos se ejecutarán localmente en entornos aislados, con versiones y configuraciones documentadas.

### Entregable

`docs/validation/MK-009-results.md`

Incluirá:

- Vulnerabilidades conocidas del laboratorio.
- Hallazgos detectados por MANTIS.
- Vulnerabilidades no detectadas.
- Pruebas omitidas y sus motivos.
- Resultados inconclusos.
- Falsos positivos identificados.
- Limitaciones del análisis.

No se presentará una vulnerabilidad como detectada sin evidencia reproducible.

## 7. Límites de alcance

MK-009 no contempla:

- Escaneos contra objetivos públicos no autorizados.
- Ejecución destructiva sin restauración verificada.
- Fuzzing ilimitado.
- Explotación automática posterior al hallazgo.
- Uso de credenciales reales de terceros.
- Despliegue de infraestructura de pago.

## 8. Criterios de terminado

- [ ] MANTIS admite múltiples identidades con límites configurables.
- [ ] Configuración de autenticación independiente por identidad.
- [ ] Matriz identidad × recurso × operación.
- [ ] Evidencia contextual para confirmar BOLA.
- [ ] Detección BOLA en GET.
- [ ] Pruebas controladas de PUT y PATCH.
- [ ] DELETE protegido por restauración verificada.
- [ ] Severidad y confianza independientes.
- [ ] Estados CONFIRMED, NOT_FOUND, OMITTED e INCONCLUSIVE.
- [ ] Credenciales protegidas en logs y evidencias.
- [ ] Límites de ejecución aplicados.
- [ ] Evaluación local contra crAPI y VAmPI.
- [ ] `MK-009-results.md` documentado y reproducible.
- [ ] Pruebas automatizadas para las nuevas capacidades.

---

**MK-009 se considerará terminado cuando las capacidades ampliadas estén implementadas, probadas y respaldadas por evidencia reproducible.**
