## 1. Objetivo del hito

Construir una API REST local que simule un sistema de facturación de dos sucursales
y permita demostrar, de forma controlada, tres clases de fallos de autorización y
lógica de negocio:

- **V1 — BOLA**: un usuario accede a una factura que no está autorizado a consultar.
- **V2 — BFLA**: un empleado ejecuta una operación reservada al administrador.
- **V3 — Salto de estado**: una factura cambia a un estado no permitido por el flujo de negocio.

El laboratorio será el **oráculo de prueba** de MANTIS: conoceremos de antemano los
fallos y podremos comprobar si la herramienta los detecta correctamente.

---

## 2. Alcance: qué SÍ entra

- API REST con FastAPI.
- Base de datos SQLite local.
- Autenticación mediante API keys de laboratorio.
- Dos usuarios: administrador y empleado.
- Dos sucursales: Norte (S001) y Sur (S002).
- Facturas ficticias con distintos estados.
- Tres vulnerabilidades intencionales y documentadas.
- Separación entre comportamiento vulnerable y comportamiento esperado.
- Datos de prueba deterministas y mecanismo para reiniciarlos.
- Documentación de endpoints, credenciales ficticias y escenarios.
- Pruebas automatizadas que demuestren tanto los fallos como los resultados
  esperados después de corregirlos.
- Ejecución exclusivamente en `127.0.0.1`.

**Regla:** los fallos deben estar aislados y ser reproducibles. No queremos que toda
la API sea un desastre de seguridad; queremos tres casos concretos que MANTIS pueda
identificar y verificar.

---

## 3. Fuera de alcance: qué NO entra

- Dashboard Django o interfaz gráfica.
- Escaneo de sitios públicos o direcciones externas.
- Importador de especificaciones OpenAPI para MANTIS.
- Motor genérico de generación de ataques.
- Ejecución automática de cadenas complejas de operaciones.
- Escaneo de puertos, fuzzing masivo o explotación avanzada.
- JWT, OAuth2, integración con proveedores de identidad o gestión de sesiones real.
- Docker, despliegue en AWS o alojamiento público.
- Datos reales, facturas reales o información personal.
- Un sistema de facturación completo con IVA, reportes contables o pagos.
- Un sistema de plugins o configuración compleja de vulnerabilidades.
- Endpoint de rechazo (`/reject`) ni transiciones adicionales más allá de las
  definidas en la sección 4.

Estos puntos pueden tener valor en el futuro, pero no contribuyen directamente al
objetivo de MK-002.

## 4. Modelo de datos

### 4.1 Usuarios

| ID | Usuario | Rol | API key | Sucursal autorizada |
|---|---|---|---|---|
| U001 | admin | admin | `lab-admin-key` | Norte y Sur |
| U002 | empleado | employee | `lab-employee-key` | Solo Norte (S001) |

Las API keys son credenciales ficticias para el entorno local, no secretos
reutilizables en producción. Se usarán únicamente para identificar al usuario y
comprobar su rol y ámbito.

### 4.2 Sucursales

| ID | Nombre |
|---|---|
| S001 | Norte |
| S002 | Sur |

### 4.3 Facturas

| Campo | Tipo | Propósito |
|---|---|---|
| id | INTEGER | Clave primaria. Es lo que va en la URL: `/invoices/1` |
| number | TEXT | Etiqueta legible: `FAC-001`. Solo para humanos y documentación. |
| branch_id | TEXT | Sucursal asociada (`S001` o `S002`). |
| supplier | TEXT | Proveedor ficticio. |
| total_cents | INTEGER | Importe en céntimos. `$12.50` → `1250`. Cero ambigüedad de coma flotante. |
| status | TEXT | Estado del flujo de negocio. |
| created_at | TEXT | ISO 8601 UTC, valor fijo en el seed. No usar `datetime.now()`. |

**Flujo de estados permitido:**

```
draft → submitted → approved
```

**Transiciones prohibidas (entre otras):**

- `draft → approved` (salto directo, es V3)
- `approved → cualquier otro`
- `submitted → draft` (retroceso)

En MK-002 no existe `rejected`. Se valorará en un hito posterior si hace falta.

### 4.4 Datos semilla

| id | number | branch_id | status | created_at |
|---|---|---|---|---|
| 1 | FAC-001 | S001 (Norte) | draft | 2026-01-01T10:00:00Z |
| 2 | FAC-002 | S001 (Norte) | submitted | 2026-01-02T10:00:00Z |
| 3 | FAC-003 | S002 (Sur) | draft | 2026-01-03T10:00:00Z |
| 4 | FAC-004 | S002 (Sur) | submitted | 2026-01-04T10:00:00Z |

Los importes (`total_cents`) y proveedores se fijarán en `lab/seed.py` y serán
deterministas. El seed **no** usará valores aleatorios ni `datetime.now()`.

### 4.5 Decisión de autorización

- El administrador (`U001`) puede consultar y gestionar ambas sucursales.
- El empleado (`U002`) queda limitado a la sucursal Norte (`S001`).
- La API debe comprobar autorización **sobre cada factura**, no solo que el
  usuario esté autenticado.
- La política se aplica en el servidor. **No se confía en un `branch_id` enviado
  por el cliente.**

## 5. Endpoints del laboratorio

Lista cerrada. **No se añadirán rutas improvisadas durante el desarrollo.**

| Método | Ruta | Auth | Rol permitido | Propósito |
|---|---|---|---|---|
| GET | `/health` | No | Público local | Comprobar disponibilidad |
| GET | `/me` | Sí | Admin, empleado | Consultar identidad y rol |
| GET | `/branches` | Sí | Admin, empleado | Listar sucursales visibles según el usuario |
| GET | `/invoices` | Sí | Admin, empleado | Listar facturas autorizadas según el usuario |
| GET | `/invoices/{invoice_id}` | Sí | Admin, empleado | Consultar una factura (sujeta a autorización por objeto) |
| POST | `/invoices/{invoice_id}/submit` | Sí | Admin, empleado | Enviar factura a revisión (`draft → submitted`) |
| POST | `/invoices/{invoice_id}/approve` | Sí | Admin | Aprobar factura (`submitted → approved`) |
| POST | `/lab/reset` | Sí | Admin | Recrear todas las tablas desde el seed determinista |

**Notas:**

- `{invoice_id}` es el `id` entero de la factura, no el `number`.
- El rol permitido indica la **política prevista**. Los fallos plantados serán
  excepciones deliberadas y documentadas (ver sección 6).
- `/lab/reset` es una utilidad de laboratorio, no una función de producción.
- No habrá endpoints de registro público, eliminación masiva, carga de archivos
  ni modificación arbitraria de roles.
- Las rutas con cambios de estado utilizan POST. No se cambian datos vía GET.

## 6. Vulnerabilidades plantadas

### V1 — BOLA (Broken Object Level Authorization)

**Endpoint:** `GET /invoices/{invoice_id}`

**Escenario:** el empleado (`U002`, autorizado solo a Norte) consulta una factura
de Sur, por ejemplo `FAC-003` (id 3).

**Comportamiento vulnerable:** la API comprueba que la API key sea válida, busca
la factura por ID y la devuelve **sin comprobar si el usuario tiene permiso sobre
ese objeto**.

**Comportamiento esperado:** tras autenticar al empleado, la API también debe
verificar su autorización sobre esa factura. Una solicitud no autorizada debe
rechazarse **sin revelar sus datos**.

**Prueba de éxito de MANTIS:**

1. Consultar una factura que el empleado puede ver (`FAC-001`, id 1).
2. Consultar una factura fuera de su ámbito (`FAC-003`, id 3).
3. Comparar ambas respuestas.
4. Registrar como hallazgo la segunda solicitud si expone datos que no deberían
   ser accesibles.

La prueba **no** debe basarse únicamente en que dos respuestas sean diferentes;
debe comprobar la regla de autorización conocida del laboratorio.

---

### V2 — BFLA (Broken Function Level Authorization)

**Endpoint:** `POST /invoices/{invoice_id}/approve`

**Escenario:** un empleado intenta aprobar una factura que está en `submitted`
(transición válida para un administrador).

**Comportamiento vulnerable:** la API valida la identidad, pero **no verifica el
rol requerido** para ejecutar la operación.

**Comportamiento esperado:** solamente el administrador puede aprobar facturas.
Una solicitud del empleado debe rechazarse y **no modificar la base de datos**.

**Prueba de éxito de MANTIS:**

1. Con el administrador, aprobar `FAC-002` (id 2, en `submitted`) y comprobar que
   la operación autorizada funciona cuando el estado lo permite.
2. Con el empleado, intentar aprobar una factura en `submitted` (por ejemplo
   `FAC-004`, id 4, que está en Sur y además no le pertenece... ver nota).
3. Verificar **tanto la respuesta HTTP como el estado persistido** de la factura.

Si la API responde con un error pero la factura queda aprobada, el control sigue
siendo inseguro. Por eso la prueba debe **revisar el efecto, no solo el código de
respuesta**.

> **Nota de aislamiento:** para que V2 no se confunda con V1, la prueba de BFLA
> debe usar una factura sobre la que el empleado **sí tendría acceso por objeto**
> si estuviera autorizado por rol. En la práctica: usar `FAC-002` (Norte,
> `submitted`) y comparar admin vs. empleado. Así el único eje que varía es el rol.
>
> **Corrección importante respecto al borrador anterior:** la prueba de BFLA debe
> usar `FAC-002` (Norte, submitted), no `FAC-004` (Sur). Si usamos una factura de
> Sur, V1 y V2 se solapan y MANTIS no puede atribuir el fallo a una regla concreta.

---

### V3 — Salto de estado (violación de lógica de negocio)

**Endpoint:** `POST /invoices/{invoice_id}/approve`

**Escenario:** el administrador intenta aprobar una factura en `draft`
(`FAC-001`, id 1), sin pasar por `submitted`.

**Comportamiento vulnerable:** la API comprueba el rol administrador, pero **no
valida la transición permitida** entre estados.

**Comportamiento esperado:** la aprobación solo se permite cuando la factura está
en `submitted`. Una factura en `draft` debe conservar su estado original.

**Prueba de éxito de MANTIS:**

1. Reiniciar el laboratorio para asegurar `FAC-001` en `draft`.
2. Con el administrador, intentar aprobarla directamente.
3. Comprobar si terminó en `approved`.
4. Registrar un hallazgo si se produjo una transición prohibida.

**Decisión de aislamiento:** V3 usa **al administrador** y una transición inválida
para **cualquier** rol. Así separamos la validación de transición de estado de la
autorización por rol.

---

### 6.4 Separación de los tres fallos

BFLA (V2) y salto de estado (V3) comparten endpoint, pero son reglas distintas.
Para que las pruebas no se confundan:

| Vulnerabilidad | Usuario | Factura | Estado de partida | Qué se viola |
|---|---|---|---|---|
| V1 (BOLA) | Empleado | FAC-003 (Sur) | `draft` | Autorización por objeto |
| V2 (BFLA) | Empleado | FAC-002 (Norte) | `submitted` | Autorización por rol |
| V3 (salto) | Administrador | FAC-001 (Norte) | `draft` | Transición de estado |

Esta tabla es la **referencia canónica** para las pruebas de MANTIS. Cualquier
prueba que mezcle ejes no debe considerarse válida para atribuir un hallazgo.

## 7. Decisiones técnicas

| Decisión | Elección | Motivo |
|---|---|---|
| Framework | FastAPI | Tipado, validación, OpenAPI automático. Dependencia **solo del lab**, no del núcleo. |
| Persistencia | SQLite (fichero local) | Sin servidor, sin coste, reproducible. |
| Auth | API keys vía header `X-API-Key` | Aísla los ejercicios de autorización sin OAuth/JWT. |
| Bind | `127.0.0.1` exclusivamente | Evita exposición accidental a la red. |
| Python | 3.14 (entorno `.venv` de MANTIS) | Coherente con MK-001. |
| Importes | `INTEGER` en céntimos | Cero ambigüedad de coma flotante. |
| `created_at` | ISO 8601 UTC, valores fijos | Determinismo del seed. |
| Arranque | `python -m lab` | Consistente con `python -m mantis`. Alternativa documentada: `uvicorn lab.app:app --host 127.0.0.1 --port 8000`. |

### Reglas de implementación

- Dependencias mínimas: `fastapi`, `uvicorn` y herramientas de pruebas.
- La API **no** realiza solicitudes salientes a otros sistemas.
- Las pruebas automatizadas tendrán datos predecibles y **no dependerán del orden
  de ejecución**.
- Los escenarios vulnerables estarán claramente etiquetados en documentación y
  pruebas.
- No se usará `--reload` en pruebas automatizadas.
- `lab/` no importa nada de `src/mantis/`. `src/mantis/` no importa nada de `lab/`.
  La comunicación es exclusivamente vía HTTP.

> **Precaución:** escuchar en `127.0.0.1` limita el acceso por red, pero no
> convierte por sí solo el programa en un entorno completamente aislado. No
> ejecutar este laboratorio con datos reales ni abrirlo mediante un túnel público.

- [ ] SQLite crea y conserva las tablas necesarias.

- [ ] Las API keys inválidas no permiten acceder a endpoints protegidos.
- [ ] V1 reproduce el acceso indebido a un objeto fuera del ámbito autorizado.
- [ ] V2 reproduce una operación administrativa ejecutada por el empleado.
- [ ] V3 reproduce una transición de estado que infringe el flujo permitido.
- [ ] Cada vulnerabilidad tiene una prueba automatizada que demuestra el fallo.
- [ ] Hay pruebas negativas que demuestran que el comportamiento legítimo sigue

- [ ] El reset (`/lab/reset`) restaura los datos semilla de manera determinista.
- [ ] La documentación explica cómo arrancar, probar y reiniciar el laboratorio.
- [ ] Los tests del laboratorio se ejecutan en menos de 10 segundos.
- [ ] Git registra el hito con una etiqueta `MK-002` y el repositorio queda limpio.

## 9. Qué NO haremos en MK-002, aunque parezca buena idea

1. No construir el dashboard todavía. Primero una API y pruebas confiables.
2. No programar el detector de MANTIS dentro del laboratorio. El laboratorio es el
   objetivo de prueba, no el escáner.
3. No implementar diez vulnerabilidades adicionales. Tres casos bien aislados y
   reproducibles valen más que una colección de fallos ambiguos.
4. No incorporar IA para detectar vulnerabilidades antes de tener un motor
   determinista.
5. No implementar un sistema completo de usuarios (registro, recuperación de
   contraseñas, gestión de sesiones).
6. No desplegar en Internet ni contratar infraestructura.
7. No confundir respuesta HTTP con prueba definitiva. Un 403, 404 o 500 no
   demuestra por sí solo que una vulnerabilidad exista o no.
8. No modificar MANTIS para que reconozca únicamente estas rutas. Las pruebas del
   laboratorio deben poder ejecutarse con solicitudes HTTP normales.
9. No mezclar la implementación vulnerable con la versión corregida sin control.
   Documentaremos el comportamiento esperado y usaremos pruebas de regresión
   cuando llegue el momento de corregir los defectos.
10. No refactorizar toda la arquitectura de MANTIS. MK-002 es un módulo de
    laboratorio acotado, no una excusa para rehacer MK-001.
